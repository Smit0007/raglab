# ADR-010: Embedding Representation Versioning and Multi-Space Compatibility

## Status
Accepted

## Context
RAGLab Phase 2 established durable chunk storage in PostgreSQL using pgvector:
`embedding vector(768)` with an HNSW cosine index (`hnsw (embedding vector_cosine_ops)`).
As the system evolves to support advanced vector representation techniques (such as Matryoshka Representation Learning / dimensional truncation to 256/512, fp16 `halfvec`, binary quantization `bit(768)`, and multi-model embedding spaces), multiple architectural risks arise:
1. **Embedding-Space Collisions**: Vectors generated by different models (e.g., `nomic-embed-text-v1.5` vs. `bge-large-en-v1.5` vs. OpenAI `text-embedding-3-small`) or different Matryoshka dimensions (e.g., 768 vs. 256) reside in non-comparable topological vector spaces. Comparing them via dot product or cosine distance produces meaningless similarity scores.
2. **Schema Inflexibility**: Storing a single fixed `vector(768)` column directly on `document_chunks` prevents zero-downtime reindexing, dual-embedding evaluation, and simultaneous multi-precision representations (e.g., binary vector for initial retrieval filter + float vector for re-ranking).
3. **Premature Destructive Migration**: Modifying applied Flyway migrations or altering `document_chunks.embedding` in place risks downtime and invalidates existing Phase 2 baselines.

## Decision
We decide to adopt an **Explicit Embedding Representation Contract** and an **Embedding Spaces Registry** backed by a Dedicated Embedding Representation Table design (`chunk_embeddings`):

### 1. Representation & Dimensionality Contract
Every stored vector belongs to a formally defined `embedding_space_id`:
- `space_id`: Canonical slug (e.g., `nomic-embed-v1.5-768-fp32`, `nomic-embed-v1.5-256-mrl`, `nomic-embed-v1.5-768-bin`)
- `model_id`: Model identifier and revision (e.g., `nomic-ai/nomic-embed-text-v1.5@rev-4a2`)
- `dimension`: Integer length (e.g., 768, 512, 256)
- `representation_type`: `FLOAT32_DENSE`, `FLOAT16_HALFVEC`, `BINARY_QUANTIZED`, `PRODUCT_QUANTIZED`
- `distance_metric`: `COSINE`, `INNER_PRODUCT`, `L2`
- `normalization`: `UNIT_L2` (strictly pre-normalized) or `NONE`

### 2. Multi-Representation Schema Evolution (Target for Phase 6)
- **Phase 2 Baseline Preservation**: `document_chunks.embedding vector(768)` remains completely intact as the canonical baseline dense float representation. No existing column or migration is dropped or rewritten.
- **Dedicated Representation Table (`chunk_embeddings`)**: When multiple spaces, Matryoshka truncations, or binary/halfvec quantizations are introduced in Phase 6, they will be persisted in a dedicated child table referencing the `embedding_spaces` registry:
  ```sql
  CREATE TABLE embedding_spaces (
      id VARCHAR(64) PRIMARY KEY,
      model_name VARCHAR(128) NOT NULL,
      model_revision VARCHAR(64) NOT NULL,
      dimension INT NOT NULL,
      representation_type VARCHAR(32) NOT NULL,
      distance_metric VARCHAR(32) NOT NULL,
      normalization_policy VARCHAR(32) NOT NULL DEFAULT 'UNIT_L2',
      is_active BOOLEAN NOT NULL DEFAULT TRUE,
      created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
  );

  CREATE TABLE chunk_embeddings (
      id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
      chunk_id UUID NOT NULL REFERENCES document_chunks(id) ON DELETE CASCADE,
      tenant_id UUID NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
      space_id VARCHAR(64) NOT NULL REFERENCES embedding_spaces(id) ON DELETE RESTRICT,
      dimension INT NOT NULL,
      representation_type VARCHAR(32) NOT NULL, -- DENSE_FP32, HALFVEC_FP16, BINARY
      embedding_fp32 vector,
      embedding_half halfvec,
      embedding_bin bit,
      created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
      CONSTRAINT uq_chunk_space UNIQUE (chunk_id, space_id),
      CONSTRAINT chk_representation_column CHECK (
          (representation_type = 'DENSE_FP32' AND embedding_fp32 IS NOT NULL) OR
          (representation_type = 'HALFVEC_FP16' AND embedding_half IS NOT NULL) OR
          (representation_type = 'BINARY' AND embedding_bin IS NOT NULL)
      )
  );

  CREATE INDEX idx_chunk_embeddings_lookup ON chunk_embeddings(tenant_id, space_id, chunk_id);
  ```
- **Separation of MRL vs. Quantization in Experimental Design**:
  - *Matryoshka Dimensional Reduction (MRL)*: Tests dimension truncation (e.g. 768 $\rightarrow$ 512 $\rightarrow$ 256) using `embedding_fp32 vector(d)` to measure loss of ranking fidelity (Recall@k, MRR).
  - *Vector Quantization*: Tests numeric precision compression (e.g. fp32 $\rightarrow$ fp16 `halfvec(768)` or 1-bit `bit(768)`) using `embedding_half` or `embedding_bin` to measure memory savings vs distance distortion.
  - *Orthogonal Combination*: A vector can be both MRL-truncated and quantized (e.g. `nomic-v1.5-256-halfvec`), registered under its own distinct `space_id`.
- **Strict Query Compatibility Guard**: The retrieval engine must reject queries that do not match the target document's `space_id`. Cross-space vector comparisons are strictly prohibited at API and service boundaries.

### 3. Reindexing and Retirement Strategy
- When upgrading embedding models, the new model writes to a new `space_id` in `chunk_embeddings`.
- The document version's query routing pointer switches to the new `space_id` only after 100% of chunks are embedded and indexed.
- The previous space remains queryable during reindexing (zero downtime) and is retired only after explicit verification.

## Alternatives Considered
1. **Single Wide Table with Multiple Vector Columns on `document_chunks`**:
   - Adding `embedding_256`, `embedding_bin`, `embedding_v2` directly on `document_chunks`.
   - *Rejected*: Causes schema bloat, requires `ALTER TABLE` migrations for every new benchmarked model, and results in wide rows with many NULLs.
2. **Bytea / Raw Binary Array Storage**:
   - Storing vectors as raw bytes and calculating distances in application code.
   - *Rejected*: Loses PostgreSQL HNSW index acceleration and native pgvector hardware-optimized distance SIMD kernels.

## Consequences
- **Positive**: Complete backwards compatibility with Phase 2 baseline; enables side-by-side A/B testing of Matryoshka vs. full embeddings and quantization benchmarks without schema thrashing.
- **Negative**: Requires joining `chunk_embeddings` when retrieving secondary representation spaces.
